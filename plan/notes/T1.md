# T1 — the class table, and why each row exists

## What was measured

- `docs/domain/classes.md` (177 lines before this task) defined the mechanism — encoding, traits, the
  rules for earning a code — but had no rows: §10 called the full table "a design artefact of its
  own".
- The old registry in `docs/domain/furntypes.md` (210 lines) classifies by the *role* an object plays
  (10 product, 20 part, 30 facade, 40 hardware); ADR 0094 removed that axis and gave the top level to
  the function family.
- Two codes were already pinned by accepted records: `30.01.02` is a wall cabinet and `40.01.01` a
  work table (ADR 0097), so the cabinet type is `30.01` with mounting variants and the table is
  `40.01` with a floor and a wall form.
- `docs/domain/classes.md` §5 and §8 used codes that no longer fit the new groups (`60.01.01`
  worktop, `60.02.01` plinth, `50.01.02.01` — a fourth level, which the encoding forbids). All are
  corrected in the same change; appliances take `60`, boards and trim `70`.
- `docs/domain/products.md` §7 names exactly two fills in version 1 — a post takes height and depth,
  a shelf width and depth — and says a drawer, a back panel and a facade need their own rules later.
  Only `30.10` and `30.11` carry a fill.

## Decisions

- **Supply gains a fourth value, `MadeInShop`** (ADR 0104): none of sheet, linear or piece describes a
  product, and forcing a cabinet into `MadeFromSheet` would derive `measure = area` and
  `nesting = member`, i.e. a whole cabinet in a cutting plan. The value also covers a part built from
  a recipe — a tamburat panel of two 8 mm skins and rails, a bent panel, a made drawer box: the
  program draws one object, the shop cuts several, and what is nested is the components.
- **A family is a heading, not a class.** `GG.00.00` carries a slug and a label but no traits: the
  members of `30` disagree about `supply` (panels are sheet, cabinets assembled, a glass shelf
  bought), so no trait set is true of the family. Types and variants are the classes.
- **A variant may change a form trait (`mount`, `extent`, `fill`) but not a stock trait (`supply`,
  `measure`, `nesting`)**; that is why the wall cabinet can be a variant and the made and bought door
  cannot be two variants of one type.
- **The channel is a class, not an article.** A made facade is nested and bored here; a bought one is
  counted, never nested and admits no in-house machining — one rule differs, so it gets its own row.
  The four facade forms are therefore types (hinged, sliding, lift-up, drawer front) with a made and a
  bought row each, and a drawer is the same pair.
- **The system is a fitting, not a door variant**: a sliding wardrobe's tracks, rollers and guides are
  a bought set (`50.11`) with an article, so the door class survives a change of supplier.
- **Hinges: two types, three variants each.** The mounting form is the variant axis; card versus cup
  hinge is the type axis, because a fourth level does not exist and the cup bore is a real difference.
  A damper is an article, not a class.
- **The trade name is the node's, not the class's.** A wardrobe is a tall cabinet, a nightstand and a
  chest are base cabinets, a dining table, a desk and a work table are one floor table; the products
  table carries the maker's name.
- **Horizontal and vertical panels are two classes, and only two.** `fill` distinguishes them for the
  empty-space tool; a shelf, a bottom and a top have identical rules and one line in every report, so
  the split stops there. The back is a third row because it is the one sheet part with no edge
  banding.
- **`host` is a code prefix.** `30` matches every storage class, `30.2` every facade, `30.01` every
  cabinet form; the table stays readable when the made and bought fronts doubled the rows.
- **Appliances are components, not products** (level `Component`, supply `piece`): bought whole, no
  parts, no envelope, no `mount`; that avoids inventing a third mount value for a built-in oven.
- **The placeholder is `80.01`**, the only class of the family `80` «Общее», «Изделие общего
  назначения». `90` stays reserved for a workshop's own family, `TT = 90..99` for its local codes.

## Ruled out

- **A code group for products** (the old `10`): 0094 removed the role axis; a product is a trait.
- **A `BuiltIn` mount value**: an appliance is not a product, so the question does not arise.
- **Separate rows for a chest, a nightstand, a wardrobe, a desk**: no rule and no line of their own.
- **Separate rows for a shelf, a bottom and a top**, and for a side and a divider: identical rules;
  the names live on the node, the parts specification carries them.
- **A second worktop row for the bought postformed slab**: it is linear stock cut and cut out the same
  way; only the supplier changes.
- **A row per sliding system**: the system is an article, not a rule of the door.
- **Aliases instead of codes where a rule differs** — a gas and an induction hob, a bar and a knob
  handle, a straight and an L-shaped worktop: no rule differs, so no code.

## Remaining for the owner

The table is written and awaits approval row by row. The decisions that are genuinely the owner's are
the `MadeInShop` value, the made/bought channel doubling the front rows, the trade-name rule that
dropped the chest, wardrobe and nightstand, and the placeholder's home in family `80`.

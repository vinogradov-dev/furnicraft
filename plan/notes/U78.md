# U78 — the shell's frame, asserted without a window

## What was measured

- U77 left `FurniCraftApp::frame(ui)` callable from a test and two tests that only proved it draws.
  The four claims U66, U72 and U73 were accepted with — "the panels narrow no view", "a click on a
  panel selects nothing", "the layouts tile the scene", "both themes checked by eye" — had no
  assertion on the real app; the pure unit tests beside them built a `Chrome` by hand.
- `frame` computed the viewport and the `Chrome` it handed to the viewport but returned nothing, so
  a test could not see the rectangles the window really used. It now returns the `Chrome`.
- `Document::viewport` computed `content = chrome.content(area)` and dropped it. The document now
  keeps it in a `#[cfg(test)] scene_rect` — the product reads nothing, a test reads the rectangle
  the frame really tiled. `camera()`, `layout()` and a `pub(crate) set_layout` are the other two
  reads a frame test needs; `projection()` now goes through `camera()` so that one is not dead in a
  release build.
- The frame's own `viewport` is the central panel's outer rect and the content is inset by
  `spacing.window_margin` (8), so `chrome.content(frame_viewport)` is 16 pt wider than the scene rect
  the document reports. The tests therefore assert the scene rect itself — its top against
  `chrome.ribbon.bottom()`, its invariance across panel states, and that both panel rects sit inside
  its horizontal span — instead of recomputing it from the frame's viewport.
- The scene tree auto-selects the first panel on its first show (`editor/cards.rs`, `initialized`),
  so "a click on a panel selects nothing" is an assertion about the selection *before* and *after*
  the click, not about an empty one.
- `egui` runs a sizing pass for a new area: the Settings modal appears on the second frame after it
  is opened, and the ribbon's measured band lags the fold by one frame. The test harness therefore
  settles: it draws idle frames until the scene rect has repeated twice.

## Decisions

- One `Harness` in `apps/furnicraft/src/frame_tests.rs` with the primitives a window has — `run`,
  `press`, `click`, `drag`, `press_at`/`release_at` — and `settle`, so a test reads state instead of
  pixels. The two U77 tests moved into it.
- A border is grabbed between the press and the release, so the layout test presses, asserts
  `Shell::divider_dragging`, releases, and asserts it is over. A full click would have ended the drag
  before the assertion.
- The modal test makes a real edit first (the rectangle tool: `R` plus two clicks) so `Ctrl+Z` has
  something to undo, then orbits with a middle drag so `F` has something to reframe, then opens the
  Settings window. Closing it at the end and pressing `Ctrl+Z` again proves the gate is the modal and
  not a dead key.
- Breaking the rules on purpose is the proof: narrowing `Chrome::content` by the panels, dropping
  `!modals` from the tool table, and dropping it from the shortcut block each fail one named
  assertion.

## Two bugs the tests found, both fixed here

- `Ctrl+Shift+0` hid both panels instead of folding them: `InputState::consume_key` ignores an extra
  `Shift`, and `Shortcuts` read the plain `Ctrl+0` pair first. The shifted pair is now read first
  (`shortcuts.rs`), and the same ordering fixes the four `Shift` tool keys (`Shift+A`, `Shift+R`,
  `Shift+C`, `Shift+D`) that the plain key used to swallow: `take_drawing_shortcut` checks the
  shifted table before the plain one. U66's note ("Ctrl+Shift+0 could not be sent reliably") was this
  bug seen from the outside.
- Folding the ribbon at runtime never gave the scene its band back: `strip_area` sets the strip's
  minimum height from the band, and `Shell::ribbon_band` read the *measured* height of the previous
  frame, so the open band was a fixed point. The fold now forgets the measurement
  (`sync_ribbon_fold`), and the band reflows to `height(open)` before measuring again. Launching a
  folded workspace was already right, which is why the sheet never saw it.

## Ruled out

- Returning a `FrameGeometry { viewport, chrome }`: the viewport is not the rect the scene uses, so
  the pair invited exactly one wrong assertion. The frame returns the chrome it used, the document
  reports the scene rect it tiled.
- Feeding `Chrome::content` the central panel's inner rect: the panel rects are measured from the
  outer one, so the panels would move 8 pt inward. The mismatch is pre-existing and cosmetic; it is
  left alone.
- An `egui_kittest` harness: one more dependency for what one `egui::Context` and `RawInput` already
  do, and U77 chose that road.
- Asserting on private fields where a shell fact exists: the tests read `Shell::divider_dragging`,
  `Panels`, `Editor::drawing`, `Document::can_undo`/`can_redo` and the drawn text; only
  `settings_open` is written directly, to close a window a test opened.

# X8 — the viewport's own colours follow the theme variant

## What was measured

- The frame's clear colour was the literal `[0.10, 0.11, 0.13, 1.0]` in `SceneFrame::default` and the
  floor grid was a `Grid::default` of four colour literals; nothing in the shell ever wrote either
  from the active variant, so the light workspace kept both.
- The edge pass already adapts: `edge_color(background)` in `crates/render/src/geometry.rs` picks
  light ink for a dark background and dark ink for a light one from the background's luminance. Only
  the background was wrong, so the edges went wrong with it.
- The only non-material scene line was the drawn path: `PATH_COLOR = [0.95, 0.72, 0.20, 1.0]` in
  `scene_build::collect_object`. Every other chain in a frame is a test fixture.
- `theme::install_with` sets both `egui` styles and then `ctx.set_theme(preference)`; `egui` keeps the
  dark/light pair and resolves *System* itself, so the active variant is `ctx.theme()`, not the
  setting — an OS theme flip while the window is open moves it too.
- The window's display state (`Display` in `document.rs`) already carried the grid switch, the edge
  list and the shadow settings from `ViewportSettings` and `ViewCluster` into every frame; the theme
  was simply not part of it.
- `Shell` was the one object every tab already borrows for the frame it draws, so it is where the
  resolved variant belongs.

## Decisions

- `scene::SceneColors::{DARK, LIGHT}` hold the clear colour, a `Grid::DARK`/`Grid::LIGHT` and the line
  ink beside the frame they paint: the values stay in the crate that owns the grid, and `scene` still
  knows nothing about `egui` (ADR 0087).
- `theme::scene_colors(egui::Theme)` is the single bridge `ui` → `scene`; `Shell::colors` caches the
  result for one frame so `Document::new`, a new tab and a settings change all read the same value.
- `SceneFrame::apply_colors` rewrites only the ink: the background, the four grid colours and
  `line_ink`. The grid's switch, spacing, extent and major count stay the viewport's, so a variant
  never turns a hidden grid on.
- A `Polyline` may leave its colour to the frame (`Polyline::in_ink`, `color: Option<[f32; 4]>`) and
  the renderer resolves it at upload. That keeps a theme switch to `apply_colors` + one upload: no
  node is evaluated, the revision does not move and the undo history stays clean.
- `sync_scene` re-applies the display and uploads when only the colours moved; `apply_viewport_settings`
  counts a colour change as a reason to upload too, so the settings window repaints in its own frame.

## Ruled out

- Pushing the theme into `evaluate` (a `SceneColors` parameter): the path ink would then be baked into
  every rebuild, so a variant switch would re-evaluate the whole tree, and the frame's ink would stop
  being display state. It also would have touched 16 test call sites for nothing.
- Re-colouring every polyline on the switch and matching the path by its old colour: a hidden rule
  that breaks the first time a chain wants the same amber for another reason.
- Deriving the light background from `Palette::chrome` at build time: the scene values would then be
  the chrome's, and the two variants' grid inks would still be literals somewhere. Keeping one pair in
  `scene` keeps "what a variant paints the viewport" in one place.
- Recolouring the screen-space overlays (contour grips, draft, size label) in this task: they are
  `egui` paint, not frame ink, and they live three files away from the frame. Recorded as debt under
  `[gizmo]` instead.

# P4 — one command per task

Research and decisions for the task that added `cargo xtask task`. It stays after the commit because
"why the tool is shaped this way" outlives the task; the outcome is in `plan/BACKLOG.md`.

## What a session had to do before

To start S14: `cargo xtask status` (five lines of ~1000 characters, because `parse_backlog` joined
every wrapped entry into one), then `grep` over `plan/BACKLOG.md` for the fields, `plan/map.md` for
the anchor, `plan/debt.md` for the area, `docs/decisions` for the cited ADRs, `git log -- <path>`
for the last change, and the production-line shell loop in `plan/refactor.md` §2.

## What was measured

- `state_contract::Task` held `id`, `status`, `section`, `text`, `files` and nothing else;
  `parse::backlog_entries` collapsed continuation lines before `parse_task_line` saw them, so
  `Why:`/`Shape:`/`Done:` existed only as substrings of a very long line (`parse.rs`).
- `plan/map.md`, `plan/debt.md` and `plan/questions.md` were read by `dashboard.rs` only, and only
  as whole-file summaries — nothing joined them to one task.
- The production-line metric lived in exactly one place, a shell snippet in `plan/refactor.md` §2,
  and its prose said "before the last `#[cfg(test)]`" while the snippet used `head -1` (the first).
  The prose is the rule; the snippet was the bug, and `line_counts` now uses `rposition`.

## Decisions

- Notes are `plan/notes/<ID>.md`, one per task, read only by `task`/`dashboard --task`, never by
  `status`. A note survives its task: research that ruled a road out stays useful, status must not.
- The gate checks a note's name (a task the backlog has), that it is not empty, and a 150-line
  budget. It no longer deletes a note when the task closes — a finished task keeps its research.
- `state-contract` owns the plan half (frames, fields, map, debt, questions, notes); `xtask` owns the
  code half (line counts, last commit, ADR titles), because `crates/` and `docs/decisions/` are
  product knowledge the generic gate must not learn.
- `task` validates the whole plan first (`check_with`): a report read from a broken plan would name
  files and tasks that no longer exist, which is worse than no report.
- `status` prints the lead sentence and one `detail: cargo xtask task <id>` hint; the hint is passed
  in by the host, so the crate names no command of its own.
- The three forms: default framed blocks for a human, `--md` for an agent (labelled, no box drawing,
  every source named), `--paths` for a shell loop. No JSON: the crate has no dependencies, and the
  agent form is already unambiguous.

## Gotchas found while building it

- `Task::text` must keep the whole entry: `validate` reads the done commit hash from its tail
  (`task.text.rsplit('`')`). The lead is a separate field for that reason.
- `find_label` needs a word start and is case-insensitive, because entries write `— rules: B1` at the
  end of the lead line while the template spells `Rules:`.
- A path mentioned in `Shape:` may not exist yet — it is what the task creates. The `files:` hint
  cannot name it (the gate rejects a dead path), so the report lists it as "to create".
- `display_width("STATE")` is 5, not 4: the ANSI test that said otherwise was wrong, not the renderer.

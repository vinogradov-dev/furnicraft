# N5 — The move rule is a snapshot in the model, and the drag reads it once.

The move rule is a snapshot in the model, and the drag reads it once.

## What was measured

- The translate gizmo was the only mover, and it already ended a drag with one
  `node.placement.set_many`: `commit_translation` quantises every placement and the engine test
  `a_placement_batch_is_one_revision_and_one_undo_step` proves the batch is one revision and one
  undo step. So N5 needed no new command and no history work.
- The `mount` trait had no consumer. `ClassCode::traits()` lives in the model, while the engine's
  `NodeRules` is a higher layer, so the rule belongs in the model as a query and reads the class
  row directly (ADR 0103, ADR 0094).
- The model already derives every world box the rule needs: a product's envelope through its
  placement (`ProductBox` in `project/query.rs`), a panel's nominal box and an object's bounds
  (`tree::panel_bounds`, `tree::object_bounds_mm`) — all in millimetres, all derived, none stored.
- A product's dashed envelope is a scene item carrying the product's own id, but
  `Target::drawables` listed only geometry ids, so the frame did not follow a drag at all.
- The `files:` hint named `crates/model/src/query.rs`, which is `NodeQuery` (the report filter).
  The move rule is a project query, so it landed in a new `crates/model/src/project/move_query.rs`
  and the hint was corrected through `cargo xtask task set N5 --field files --files …`.
- `TranslateGizmo::update` had no test before this task and has none after: the drag needs a live
  `egui::Ui` pointer state. The task's Done asks for the pure constraint math, so the drag path is
  covered by the rule's tests plus the commit test in `translate_gizmo`.

## Decisions

- `Project::move_rule(moving) -> Option<MoveRule>` reads the moved boxes, the other surfaces and
  the mount trait **once**, when the drag starts. `MoveRule::limit(axis, proposed)` then answers
  every pointer position without walking the document, so the frame path stays free of scans.
  Nothing is stored and the document is not mutated.
- A drag is furniture when every top-most moved node is a product or sits inside one. Free geometry
  and a loose panel keep the old exact micrometre move, which is what the task calls right.
- `Mount::Floor` zeroes the vertical distance of the whole drag; `Mount::Wall` leaves it free. Any
  floor-bound product in the selection binds it, because the selection moves rigidly. A class row
  without a mount has no rule — no product row is in that state today.
- Contact is AABB against AABB along the axis, because every surface the model can answer today is
  a box. Across the movement the boxes must share a volume; along it a body stops at a body and a
  shell stops at a shell, and a shell may contain or be contained, stopping only at the wall it
  would cross (ADR 0102). Touching faces are contact, not overlap.
- A pair that already shares a volume without containing one another is left alone: the tool did
  not create that state and blocking it would lock the maker out of the piece.
- Snapping: a surface within 5 mm captures a face of the moved box; otherwise the drag rounds to
  the 1 mm grid. Candidates are the floor and both faces along the axis of every obstacle whose
  cross-section meets the moved box, so a part in the far corner cannot pull a drag, and a face
  behind the pointer never captures it (no backwards twitch).
- The answer is quantised to whole micrometres in the model, so the preview and the placement that
  records it are the same number; `commit_translation` then rounds to the identical value.
- The product id joins `Target::drawables`, so the dashed frame follows the drag. Only products are
  added: a camera or a light drag still lists no drawable and still skips the geometry upload.

## Ruled out

- A second move tool or a furniture-only mode: the owner asked for the current tool to do the
  right thing, and a mode would make a piece movable two ways.
- A `mount` field on the container: the class row owns the trait and N1 made it the definition.
- The engine as the rule's home: the rule is a derived query over the document, and the engine
  would have to hand the gizmo a copy of the answer anyway.
- Snapping generic geometry to the millimetre grid: the task says the current free move is right
  for geometry, and a 1 mm grid would coarsen every primitive in a free scene.
- A screen-space snap radius: it needs the camera, and the task placed typed distances and the
  distance field in N8; a fixed 5 mm is the maker's own tolerance and stays honest at every zoom.
- Implementing the ray probe and the niche here: N6 owns `probe`/`niche` with its own tests; the
  mover shares exactly the surface boxes that probe will report, so the two cannot disagree about
  where a surface is.
- A new command for a constrained drag: the rule changes the delta, not the operation, so the
  release still dispatches one `node.placement.set_many` and the drag stays one undo entry.

## Verification

Unit tests over the pure rule (mount by two class rows and one changed row, contact both ways,
containment, body-versus-shell, grid and face snapping, a turned product's world box, the floor
snap, a non-finite proposal) and two app tests (the previewed distance reaches contact exactly and
one commit carries it; a loose panel keeps its exact distance), plus the envelope-preview test.
`cargo xtask ci` is green. No live run: the task asked for the pure constraint math.

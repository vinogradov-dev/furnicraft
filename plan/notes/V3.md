# V3 — the frame joins the box editor

## What was measured

- V2 shipped a box editor whose grips read exactly one owner: `BoxBody::read` demanded an
  `Object` with a `Cuboid` primitive, `GripEdit` carried a `Primitive`, and `apply_grip_edit`
  dispatched `object.primitive.replace`. A product frame stores the same three lengths as its
  authored envelope on a `Container` (ADR 0097), so the grips could not see it at all.
- `BoxDraft` had no owner: `Editor::arm_box()` always built a cuboid, `box_tool()` answered
  `PrimitiveKind::Cuboid`, and `Editor::commit_box` dispatched `object.primitive.create`.
- The task's Shape and `docs/domain/products.md` §9 say a selected **frame** shows **eight** corners
  and six faces, while V2's note records the measured box rule as **ten** grips (four base corners,
  six faces). The two are not the same count, and the difference is not a typo in one of them: a
  solid box was drawn from a base rectangle, a frame reserves a tall box whose top corners are the
  ones a standing maker can reach.
- `product.create` already existed and already takes the envelope, the class and the placement, and
  `Project::product_placement` puts a card-made frame beside the nearest piece; the drawn gesture
  has a placement of its own, so it does not use that rule.
- The ribbon's *Product frame* cell was a one-method cell (`ToolKind::Product` → the card), and the
  ribbon already had the mechanism this needs: a tool with a second input method is a split cell
  whose main face runs the method the workspace pinned (U74, `VariantSpec`, `ToolKind`).

## Decisions

- **One `BoxOwner`, one draft, one edit path.** `BoxOwner::Cuboid` and `BoxOwner::Product` are the
  two fields the three lengths can live in; `BoxDraft` carries the owner it was armed for,
  `BoxBody` carries the owner it read, and `BoxChange` is the field the drag writes. The commands
  stay the owners' own: `object.primitive.replace` and `product.envelope.set`, then the same
  `node.placement.set` compensation for a moved zero. Nothing gained a preview path and a drag is
  still one edit scope, one undo entry.
- **A solid keeps four base corners; a frame shows eight.** The corner drag plane is the horizontal
  plane *through that corner*, so a top corner reads the ceiling and moves width and depth exactly
  as a base corner reads the floor. That keeps the task's "a corner changes two sizes" true for both
  rings, needs no new gesture, and gives a two-metre cabinet handles at eye level. Changing the
  cuboid to eight corners would have added four duplicate handles to a box the maker drew as a base
  rectangle; V2's decision stands and the difference is documented in the module and in
  `docs/domain/products.md` §9.
- **The frame is drawn through the box tool, not through a second draft.** `arm_box(BoxOwner::Product)`
  is the same draft, the same prism paint and the same ✓; only `commit_box` branches, and the frame
  goes to `product.create` at the scene root with the placeholder class, then is opened and armed for
  its parts exactly as the card's create does. A test asserts that the card and the gesture produce
  the same `Project` for the same three sides, so the two entries cannot drift.
- **The ribbon's frame cell is a split cell: the card is the tool's own method, the draw is its
  second.** The card was the only entry before, so it stays the primary and the drawn method is one
  row down (`furniture.product.frame.draw`, *Frame by drawing*). The cell's pressed state shows on
  the drawn row while the draft lives, so the list is not silent about the tool being armed.
- **The gesture names nothing but the placeholder.** A pointer gesture cannot pick a class, so the
  drawn frame takes «изделие общего назначения» — the same default the card takes when its class is
  left alone — and the name is that class's label in the current language, so the two entries agree
  on the document and not only on the envelope.
- **The height bar says which box it sizes.** The pull's command bar read *Box height*; a frame's
  pull is its reserved height, so the bar reads *Frame height* (`Message::FrameHeight`) while the
  draft's owner is the product.

## Ruled out

- **Making both owners show eight corners.** It is one grip set instead of two, but it adds four
  handles to every solid box for no gesture a solid needs; the visual cost is real and the benefit
  is none, because a box is small and its base is what was drawn.
- **A separate `ProductBoxDraft` and a second preview.** The whole point of ADR 0101 is one toolkit;
  a second draft would fork the prism, the step, the command bar and the escape path.
- **Letting the drawn frame keep the armed container as its parent.** A product may not sit inside a
  product (products invariant 3), and the card already creates at the root; so does the gesture.
- **Shipping the live-run eye check.** The task asks for a live run of the drag feel; this session
  drives a real pointer drag through the real frame headlessly (press on the frame's far corner, move
  inward 100 mm on both axes, release, one undo) instead of opening a window on the owner's screen.
  The grips themselves were checked as pixels: `target/ui-shots/frame-grips.png` shows the reserved
  box with eight corners and six faces.

## Verification

- `cargo xtask ci` green.
- `frame-grips.png`: the open frame's dashed envelope is drawn in the active ink, its eight corners
  sit on the box's top and bottom rings, and the six face grips sit on the face centres.
- `frame_tests::a_drag_on_a_frame_corner_resizes_the_envelope_in_one_undo_step` drives the pointer
  through the frame: the envelope shrinks 100 mm in width and depth, the revision moves once, and one
  undo restores 600 × 560.

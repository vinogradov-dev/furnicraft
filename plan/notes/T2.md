# T2 — the class registry is data in the model, and the program can see what it is look

the class registry is data in the model, and the program can see what it is looking at

## What was measured

- `furntype.rs` (196 lines) validated the *shape* of a code only: `20.01.09` passed `from_code`, so no
  algorithm could ask what an object is. `docs/domain/classes.md` §7 holds 65 assignable class rows in
  eight family headings; §3–§5 hold the encoding, the inheritance rule and the trait semantics.
- Twelve sites named the old value: `properties.rs` (`PropertyValue::FurnType`, `SYSTEM_FURNTYPE`),
  `query.rs`, `project/query.rs`, `container.rs`, `lib.rs`, `fixtures.rs`, the UI property card and
  scene-tree badge, one engine test, `document.md` and `PROJECT.md`.
- The stored tag is part of the schema (`"kind": "furntype"`), so the rename is a schema bump
  (ADR 0096: no migration), and five JSON fixtures plus the golden scene carried `20`.

## Decisions

- `crates/model/src/class.rs` replaces `furntype.rs`: `ClassCode` (shape-valid, registry-optional),
  `ClassPrefix` (`30.2` is a set, `30.02` a code — a digit prefix, not a `ClassCode`), `OperationSet`,
  `TraitSet` as one `u32` mask with one accessor per trait, `ClassRow`, one `REGISTRY` const table and
  `registry()` for the picker.
- Labels are `furnicraft_text::Message` variants, so the model now depends on `furnicraft-text` (L0 →
  L1). ADR 0094 names `label_key` in that crate, and §7's English/Russian columns become the 73 rows
  of its table; a model test compares both languages with the document.
- Lookup is a binary search over a table kept ascending; a test proves the order, the parent of every
  row and that a family carries no traits.
- Inheritance is checked once, by a test, never walked: a variant agrees with its type on `supply`,
  `measure`, `nesting`, `level` and `opening`, may add operations but never drop one, and may narrow
  `host` but never widen it. `check_table` judges the shipped table and a synthetic contradiction, so
  the rule has a failing case.
- Assignment (`Properties::insert`) refuses an unknown code or a family heading; loading validates the
  kind only, so a number the registry lost survives a file. `000000` stays assignable: it is the
  default of every node and the property card writes it when a class row is added.
- Schema `20 → 21`; the golden scene and the engine's five diagnostics fixtures follow it.
- `docs/domain/classes.md` §7's family heading line now carries the two labels the registry stores,
  and §3's inheritance sentence says a variant may narrow `host` (see below).

## Ruled out

- A linear scan or a per-code `match`: 65 rows, and a sorted table costs one binary search and no
  allocation.
- Nine boolean/trait fields on `ClassRow`: the mask keeps a row one value and every accessor a shift.
- Deriving `measure`/`nesting` at row construction: `30.14` glass shelf is the one documented
  override (bought by area), so each row states the pair and a test proves the derivation for the
  other 64.
- Keeping the `furntype` serde tag with an alias for older files: ADR 0096 forbids a past before 1.0.
- Teaching the UI the class tree, the labels and the trait gates here: T3 draws the picker and T4 the
  gates, so this change only renames the call sites it had to touch.
- The row fields `since`, `retired` and `aliases`: no consumer exists before the picker and the
  registry changelog, and a field nobody reads is speculation (AGENTS §4). T3 reads `label()` and
  `registry()`; `retired` arrives with the first withdrawn row.

## For the owner

- ADR 0094 says a variant's `host` must *contain* its type's, but the approved `50.03.03` undermount
  runner narrows `50.03`'s `30.10` away and keeps `30.3` — physically right, a runner under the drawer
  is not screwed to a side panel. The table is the authority, so §3 now reads "may narrow but never
  widen" and the test enforces that. Recorded in `plan/questions.md` for confirmation.

# X33 — a drag on the UI scale reads the pointer's travel, not its place.

a drag on the UI scale reads the pointer's travel, not its place.

## What was measured

- The drag was read as `total_drag_delta()`: the difference between the pointer's place now and its
  place at the press, both in *points*. `points = pixels / (zoom × native)`, and the UI scale is the
  zoom, so every frame of a drag rescales the coordinate system the drag is measured in. A pointer
  standing still at x = 810 px keeps its pixel position and changes its point position: with the zoom
  at 1.04 the same place reads 779 points, which the field counted as −31 points of travel.
- Consequence: a loop. Drag right → the value climbs → the zoom grows → the point delta turns
  negative → the value falls → the zoom falls → the point delta turns hugely positive → clamp to 200
  → clamp to 75. The value the control reports (`ui_scale::show` writes the applied percentage back)
  is the last frame's, so `settings.json` kept whatever the loop ended on, and the next launch opened
  at that scale — 75 % was seen.
- Reproduced without a mouse: `physical_input` in `ui_scale`'s tests now builds the frame the way the
  window backend does — the monitor's native density in `ViewportInfo`, `screen_rect` in points, every
  pointer position converted with `ctx.pixels_per_point()` of that moment. Pressing the field at
  (780, 460) points and moving 2 physical pixels a frame ten times gave
  `100, 101, 104, 105, 90, 87, 154, 171, 75, 200`.
- The control sits far from the window's origin in the real window (the Settings modal is centred),
  which is what makes the error large: the point coordinate that gets rescaled is ~800, not ~5. A
  test that drags the field at the top-left corner of the screen does **not** reproduce it.

## Decisions

- The field measures the pointer's own travel. `Response::drag_motion()` (through
  `PointerState::motion()`) gives the raw motion `winit` forwards from `DeviceEvent::MouseMotion` as
  `Event::MouseMoved`; it is a movement, not a coordinate, so nothing on screen can feed back into it.
  It is taken in the platform's own unit — winit's Wayland backend sends the relative-pointer delta in
  surface-local units and X11 sends raw device units, so a fixed normalisation would be wrong on one
  of them, and the unit only changes the rate, never the stability.
- Without raw motion the field falls back to the pointer's *place*, read as a difference between two
  places in the pixels of the scale each was measured at. That needs the scale the backend used for
  the events of this pass, which is the previous pass's `pixels_per_point`: `egui` applies a zoom
  change at the start of a pass. The widget keeps that one `f32` in `ui.data` under
  `id.with("events_scale")`.
- The travel accumulates from the value the button went down on, in `ui.data`, so a caller that
  rebuilds its draft from the document every frame (as `millimetre_field` does) still advances.
- `egui` calls a press a drag only after the pointer has moved a few points, and that trip arrives as
  movement before `drag_started`: the first dragged frame seeds the accumulator from
  `total_drag_delta` in the press's pixels (nothing has rescaled the window yet at that moment) and
  records the place it should measure from next frame as the *current* place, not the press's.
- The accumulation is not clamped while dragging, only when written, so a drag past an end comes back
  as soon as the hand comes back instead of unwinding a spent overflow.

## Ruled out

- Keeping the positional drag and clamping harder: the loop is in the measurement, not the clamp; a
  clamp only chooses where the oscillation sticks.
- Dividing the raw motion by the native density to make "points at 100 %": winit's two backends
  already disagree about the unit (surface-local on Wayland, device units on X11), so one divisor is
  wrong on one of them; the rate differs by the density, the jitter does not.
- Applying the zoom only when the drag ends: it removes the feedback, but the window would rescale in
  one jump after the release instead of following the hand. The raw-motion measurement keeps the live
  preview, which is what the control is for.
- Measuring from `pointer.delta()` and compensating with the ratio of the two frames' scales: the
  ratio is known, the scale each *event* was converted with is not, and the remaining error is again
  proportional to the pointer's distance from the window's origin.

# U52 — the scale scrubs on its delta and offers presets.

the scale scrubs on its delta and offers presets.

## What was measured

- `ui_scale::show` drew an `egui::Slider` over 75..=200 with `step_by(5)`, and the value came from
  the pointer's place along the track. `ctx.set_zoom_factor` re-lays out every widget, so the track
  moved under the pointer while the drag ran and the handle chased it: the reason a slider is the
  wrong control for a value that resizes its own widget.
- Five other numeric fields in `crates/ui` scrubbed through `egui::DragValue`:
  `settings.rs` (roll ring step, grid step), `properties_card.rs` (an integer property),
  `panel_card.rs` (`millimetre_field`), `light_card.rs` (three colour components, intensity).
- egui 0.37 has two drag deltas and they are not the same thing: `Response::drag_delta` is the
  movement **this frame** (`pointer.delta()`), `Response::total_drag_delta` is the movement from
  where the button went down. `DragValue` uses the per-frame one and keeps a precise value in egui
  memory to accumulate it.
- `Memory::request_focus` grants focus in the same frame, so the next frame is not a "gained focus"
  frame: a select-all keyed on `Response::gained_focus` never runs after a click. The click has to
  write the text-edit state itself.
- `Context::set_zoom_factor` takes effect at the start of the next pass, so `ctx.zoom_factor()` is
  still the old value in the frame that set it. The percentage stored in `settings.json` was read
  back from the context in that frame, which left the stored scale one drag step behind.

## Decisions

- `crates/ui/src/scrub.rs` holds one `Scrub` widget: a `Button` that senses click and drag, and a
  `TextEdit` while it holds the focus. The drag stores the value it started on and adds
  `total_drag_delta().x * speed`, so neither the field's width nor the pointer's place can move the
  number, and `ui.set_cursor_icon(CursorIcon::None)` hides the pointer for the drag.
- Typing replaces the number (the whole text is selected when the field starts editing), is parsed
  with a comma as the decimal point, clamped to the field's range and written on Enter or when the
  focus leaves. A typed text that outlives its edit frame is applied by the next frame that draws the
  button — that is a click into another widget.
- `Scrub` replaces all five `DragValue` call sites, so the rule "read the delta, hide the pointer" is
  one implementation rather than one per card.
- `ui_scale::show` takes `&mut u32` and writes the percentage it applied into it: the stored scale is
  the one the user sees, and it no longer lags a pass behind. The six presets are `selectable_label`s
  that set their own percentage exactly.
- Verified by looking: the app was run on this desktop with the Settings window open on *Appearance*
  (Russian), and the field plus the six preset buttons fit the 430-point page above the hint line.

## Ruled out

- `egui::DragValue` with a zero speed and our own drag maths beside it: it would keep its own text
  formatting and editing, but it paints its number from the value it computed before we overwrite it,
  so the field would show one number and hold another for a frame.
- Handing `DragValue` the real speed and only adding the cursor rule: it reads `delta.x - delta.y`,
  so a vertical drag would change the value, which the task rules out.
- Reading `ui.input(|i| i.pointer.delta())` per frame and accumulating: it needs the accumulated
  value in egui memory (a caller that rebuilds its draft from the document every frame, such as
  `millimetre_field`, would otherwise advance one frame's delta per frame), and the total from the
  press is the same information without the state.
- Keeping the slider beside the field: two controls for one value would disagree for a pass after
  either moves.

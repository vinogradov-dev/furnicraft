# U80 — the interface rules are parsed, not remembered

## What was measured

- `crates/ui` carried 25 colour literals outside `theme.rs`: sixteen `Color32::LIGHT_RED` error
  labels, a `Color32::YELLOW` warning glyph, one `Color32::from_rgb(230, 180, 80)` collapse warning
  and one `from_black_alpha(160)` Home backdrop. None of them followed the light palette, and a
  palette change would have missed every one.
- `crates/ui` and `apps/furnicraft/src` create hosts in thirteen shipped modules: the window
  skeleton (`main`), the header band, the file dialogs, the two side panels, the status row, the
  view cluster, the ribbon strip, the contour number popup, the command bar, the palette, Settings,
  Home and the ribbon's variant list. The task named seven; the other six were already legitimate
  surfaces that had no row.
- `icons.rs` owns the six role inks (ADR 0090) and `settings.rs` converts the stored accent with
  `Color32::from_rgb(r, g, b)`: both are colour *data*, not a hand-picked channel.
- The shell's gizmo overlays carry their own fixed inks; `plan/debt.md` `[gizmo]` already records
  them as the leftover of X8.

## Decisions

- `xtask/src/ui_rules.rs` parses every shipped `.rs` under `crates/ui/src` and
  `apps/furnicraft/src` with `syn`. The import table resolves `use egui::Color32 as C` and
  `eframe::egui::Area`, so an alias is caught by the same rule.
- A colour is **literal** when `Color32::from_*` is called with literal arguments only, or when a
  named ink (`Color32::WHITE`, `Color32::LIGHT_RED`) or a raw struct literal is used. A colour
  converted from data (`from_rgb(r, g, b)`) is not a literal, which is why `settings.rs` needs no
  row and `icons.rs` does: its role table is twelve hand-picked values.
- `TRANSPARENT`, `PLACEHOLDER` and `NONE` are sentinels for "no colour", not palette entries, and
  are allowed everywhere.
- The colour rule reads `crates/ui/src` only; the shell's gizmo inks are the recorded debt and are
  not re-litigated here. The host rule reads both trees because an overlay outside its owner is the
  bug in either one.
- The host set is `Area`, `Window`, `Modal`, `Panel`, `SidePanel`, `TopBottomPanel`, `CentralPanel`
  and `Popup`. `Modal` joined the task's list because the file dialogs and the close question are
  modal surfaces too, and the palette, Settings and Home already needed a row.
- `HOST_OWNERS` is the whole inventory, one row per owning module with the surface it draws. A new
  surface adds a row; a feature module cannot add an allowance comment instead.
- Test code is not shipped code: a `#[cfg(test)]` item is skipped and a module declared under
  `#[cfg(test)]` (or a file only reached through one) is not read. A test may drive whatever
  `egui::Context` host it needs.
- `cargo xtask ui-rules` joins `ci` directly after `layers`, before the plan and the docs, and
  `the_real_tree_passes` runs the same check from `cargo test`.

## What the rule changed

- Every `LIGHT_RED` label now reads `theme::danger(ui)`, the warning glyph and the collapse warning
  read `theme::warn(ui)`, and the Home veil is `theme::scrim()`: one new named value in `theme.rs`
  for a modal backdrop that is deliberately neutral in both variants.
- `home.rs` and the cards no longer import `Color32`; the colour decision lives in one module again.

## Ruled out

- Moving the icon role table into `theme.rs` to keep a single owner row: ADR 0090 puts the literals
  in the icon module because the master writes them, and the theme maps them. A second row that
  says so is more honest than a table that pretends the values are palette entries.
- Refusing every `Color32::from_rgb`, including `settings.rs`'s `from_rgb(r, g, b)`: that is a
  conversion from the user's stored accent, not a hand-picked channel, and refusing it would force
  a helper whose only job is to hide the conversion from the check.
- A text search for `Color32`: it cannot see an alias, and the task's whole point is that a parse
  can.
- Covering `apps/furnicraft/src` with the colour rule now: it would fail on the recorded gizmo
  debt, and an exemption list in the feature code is exactly what the owner table avoids.
